# Français et anglais

Le routage Astro existant sert le français sous `/` et l’anglais sous `/en/`. Les mêmes composants rendent les homepages, catalogues, cartes, études, interactions et éléments de navigation. Aucune bibliothèque i18n ajoutée.

## Contenu et traductions

- `src/i18n/ui.ts` : navigation, CTA, thème, copie d’email et messages des relations technologies/projets.
- `src/i18n/pages.ts` : catalogue, recherche, compteurs, état vide et structure des études. `formatMessage()` injecte les variables nommées et signale une variable absente.
- `src/i18n/skills.ts` : noms anglais des concepts ; les technologies et noms de patterns gardent leur orthographe officielle.
- `src/data/home.ts` : introductions et titres de sections, sélection de compétences et technologies. Le contenu EN n’ajoute aucun projet ou niveau d’expérience.
- `src/data/profile.ts`, `experience.ts`, `education.ts`, `engineering-focus.ts` : contenus localisés. Institutions et noms de projets conservés. Téléphone public explicitement fourni en V3.1 ; aucun niveau CEFR, nouvelle contribution ou CV traduit inventé.
- `src/data/project-narratives.ts` : 14 résumés et récits FR/EN. `project-details.{fr,en}.ts` garde problèmes, fonctionnalités et limites ; identités, repos, stacks, catégories et relations restent communs dans `projects.ts`.
- `src/i18n/v3.ts`, `project-videos.ts` : textes du Hero et des illustrations, CTA vidéo et sources bilingues. V3.2 partage la même structure de Hero, quatre cartes Formation, catalogue et études entre langues.
- `src/content/case-studies/{fr,en}/` : cinq études par langue. Titres/SEO, aperçu et textes des diagrammes dans le frontmatter ; décisions, spécificités, vérification et limites dans le Markdown.

Pour ajouter un texte UI, créer la clé FR et sa rédaction EN dans le même dictionnaire. Les types imposent les mêmes clés ; les tests vérifient les clés et valeurs non vides. Les données éditoriales publiques exigent les deux langues. Ne pas ajouter de fallback silencieux vers le français.

Pour ajouter un projet, définir une seule identité et une seule stack vérifiée, puis les textes dans les deux fichiers éditoriaux. Mettre à jour l’inventaire audité et les contrôles de sélection concernés. Les fonctionnalités et limitations doivent conserver le même périmètre et le même nombre d’éléments. Les liens et filtres se génèrent depuis les données communes.

## Études et diagrammes

Pour modifier une étude, garder les deux Markdown alignés. Le composant `ArchitectureDiagram.astro` est unique : les 13 diagrammes ont une seule logique SVG, avec textes visibles, description accessible, légende et lecture textuelle issus de la langue de la page. Les IDs des diagrammes, le nombre d’étapes, les technologies principales et les compétences démontrées sont identiques dans les deux langues.

`validateStudyParity()` s’exécute pendant le build via `publishedCaseStudy()`. Il exige une étude publiée dans chaque langue pour les cinq projets phares et compare sources, sections, nombre de sous-sections, limites et structure des diagrammes. Une section nouvelle doit être ajoutée à la correspondance des titres dans `src/utils/i18n-parity.ts`. Ce contrôle structurel détecte des oublis ; il ne prouve pas à lui seul l’équivalence sémantique d’une traduction.

Les bénéfices techniques restent présentés comme conséquences générales des choix observés. Les limites de validation des fournisseurs, du matching, du cube SSAS et du notebook sont conservées. Les responsabilités individuelles non confirmées restent omises.

## Switch FR/EN

Le switch indique la langue active en texte souligné avec `aria-current`, et propose un lien vers l’autre langue. Les noms de langue du lien sont exprimés dans la langue cible. Sans JavaScript, la route correspondante fonctionne déjà.

Le helper `switchLocation()` conserve, pour les catalogues, `category`, `technology` et `q`. Les contrôles mettent à jour l’URL avec History API ; le lien de langue relit l’état courant à l’activation. Les ancres communes (sections de homepage et structure partagée des études) sont conservées. Les ancres propres aux titres Markdown traduits sont abandonnées pour éviter une cible inexistante. Les pages QA ont des destinations explicites ; les 404 pointent vers leur équivalent.

Les résultats de recherche portent sur les textes de la langue courante. Les IDs de catégories/technologies restent stables. Les relations entre projets ne sont jamais dupliquées par langue.

## SEO et 404

`html lang`, descriptions, Open Graph et schémas suivent la locale. `og:locale` et `og:locale:alternate` utilisent `fr_FR` et `en_GB`. Le statut étudiant du schéma Person est traduit ; sameAs et codeRepository restent identiques, sans téléphone ni auteur individuel supposé.

`SITE_URL` reste la véritable origine publique future. Sans origine, pas de canonical ou hreflang artificiel. Avec origine, chaque page publique expose canonical propre, alternates réciproques FR/EN et x-default vers FR. Les routes QA et 404 gardent noindex et n’exposent pas de canonical/hreflang. Le statut général d’indexation reste désactivé jusqu’à la validation de publication.

La page française `/404.html` et l’anglaise `/en/404/` réutilisent le même composant. La configuration Netlify prépare un fallback 404 pour les chemins EN inexistants, après priorité aux fichiers existants. Aucun hébergement n’a été publié pour le vérifier à distance.

## Vérification locale

Après `npm run build` :

```sh
npm run check:links
npm run check:design-system -- --i18n
node scripts/check-i18n-seo.mjs
```

Le dernier script construit uniquement une fixture dans `.qa/seo-build/` avec l’origine réservée `https://portfolio.example` injectée dans son processus enfant. Il vérifie le HTML des 32 routes publiques FR/EN, les cibles hreflang et les exclusions QA/404. Cette origine n’est pas configurée dans le projet ni injectée dans `dist/`. Le build normal conserve sa stratégie sans origine.

QA Chrome : sept pages principales EN × quatre largeurs (375, 768, 1024, 1440) × deux thèmes = 56 cas. Contrôles de parité des routes et langue sur les 37 fichiers HTML, liens entre locales réservés au switch, menu, filtres, recherche, singulier/pluriel, interactions, thème, copie d’email et fallback sans JS. Quatorze contrôles de régression FR à 320/375 px. Captures locales dans `.qa/i18n/` ; aucune publication.

Le total de Phase 8 était de 37 HTML / 39 routes. Depuis la Phase 10, le build de production exclut les trois pages QA : **34 HTML / 36 routes** (32 pages de contenu, deux 404, robots et sitemap). Le build QA isolé conserve 37 HTML / 39 routes. Les contrôles i18n sur dist/ utilisent désormais le nombre de pages de production dérivé des projets ; la fixture SEO conserve les pages QA pour vérifier leur noindex et leur absence de canonical/hreflang.
